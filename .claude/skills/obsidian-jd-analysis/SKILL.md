# Obsidian JD Analysis

## 시작 전 확인

1. `obsidian vaults verbose`로 대상 vault를 확정한다. 사용자가 별도 지정하지 않으면 main vault만 사용한다.
2. `jd-analysis/`의 기존 노트, `JD 분석 MOC`, 유사 역할 노트를 읽어 frontmatter·제목·내부 링크 관례를 따른다.
3. 공고 원문을 확보한다. 사용자가 전문을 붙여 넣거나 제공한 파일이라면 전문을 보존할 수 있다. URL로만 읽은 제3자 공고는 원본 링크와 검증된 섹션별 스냅샷만 기록하고, 전문 보관이 필요하면 사용자에게 원문 제공을 요청한다. 공고가 바뀔 수 있으므로 `checked_at`과 원본 URL을 기록한다.

## 파일과 자산 배치

- 분석 노트는 회사별 하위 폴더를 만들지 말고 `jd-analysis/YYYY-MM-DD-회사 역할 요약.md`에 평평하게 저장한다.
- 접두 날짜 형식은 `YYYY-MM-DD-`다. 이중 하이픈을 쓰지 않는다.
- 새 파일은 기존 `jd-analysis` frontmatter 스키마를 따른다. 최소한 `id`, `type: jd-analysis`, `aliases`, `tags`, `company`, `role`, `experience`, `location`, `employment_type`, `status`, `checked_at`, `source`, `related`를 문맥에 맞게 작성한다.
- 생성한 이미지는 `jd-analysis/assets/`에 PNG로 저장하고, 노트에서는 `![[assets/<파일명>.png]]`로 임베드한다. 회사별 자산 폴더와 SVG는 만들지 않는다.
- 기존 노트의 파일명·링크·자산은 사용자가 요청하지 않는 한 이동하거나 교체하지 않는다.

## 노트 구조

H1 바로 아래에 원문 공고를 배치한다. 사용자가 제공한 전문이 있으면 회사/포지션 정보, 소개, 팀 설명, 주요 업무, 자격 요건, 우대사항, 복지, 전형, 제출서류 등 모든 섹션과 문장을 보존한다. URL로만 읽은 제3자 공고라면 제목을 `원문 공고 스냅샷`으로 하고, 원본 링크와 섹션별 사실 요약을 넣는다. 원문에 없는 내용은 원문 블록에 보태지 않는다.

Obsidian 리딩 뷰에서 동작하는 네이티브 접기 callout만 사용한다. HTML `<details>`/`<summary>`는 사용하지 않는다. callout 내부의 모든 비어 있지 않은 줄에는 `>`를 붙여 실제로 접히는 블록 안에 들어가게 한다.

```markdown
# 회사 - 역할 JD 분석

## 원문 공고

> [!quote]- 원문 공고 전문 보기 · 확인일 YYYY-MM-DD
>
> [회사명](공식-회사-또는-공고-링크) · 위치 · 경력
>
> ### 포지션명
>
> 원문 소개 문단
>
> ### 주요 업무
>
> - 원문 항목
```

원문 블록 뒤에는 공고 해석을 작성한다. 공고에 맞춰 다음 섹션을 선택해 사용한다.

- `## 한 줄 판단`
- `## 기본 정보`
- `## 공고가 말하는 실제 문제`
- `## 자격 요건 해석`
- `## 이력서·면접 포인트`
- `## 지원 전 확인할 사항`
- `## 비교 관점`
- `## 아키텍처 구조도`

관측 사실과 해석을 분리한다. 공고에 명시된 기술·요건은 단정적으로 쓸 수 있지만, 조직 구조·실제 제품 구성·데이터 흐름·특정 벤더 채택은 추론임을 명시한다. 인용과 해석을 섞지 않는다.

## 아키텍처 이미지

공고의 기술 스택·자격 요건·우대사항을 근거로, 이해에 필요한 수만큼 이미지를 계획해 생성한다. 목표는 기술 키워드 요약 카드가 아니라, 독자가 한 화면에서 **누가 어떤 진입점으로 들어와 어떤 플랫폼 계층·데이터 경로·운영 체계를 거치는지** 따라갈 수 있는 상세 아키텍처다. 기본적으로 다음 두 관점을 제공한다.

1. `1차 도출`: 공고에 언급된 기술스택을 기반으로 아키텍처 구조도를 제공한다.
2. `추론`: 공고 원문에서 합리적으로 확장한 운영/배포/보안 흐름을 담아서 아키텍처 구조도를 제공한다.

### 생성 전 설계

이미지마다 먼저 다음을 짧게 설계하고, 그 항목이 그림 안에서 실제 컴포넌트 또는 화살표로 드러나게 한다.

1. **행위자와 진입점**: 사용자, 운영자, 외부 고객 환경, 내부 시스템 등 공고가 암시·명시한 주체와 요청/관리/배포의 출발점.
2. **실행·플랫폼 계층**: Bare-metal, VM, Kubernetes, GPU 노드, 컨테이너, 애플리케이션/서비스처럼 공고에 나온 실행 단위와 소속 경계.
3. **데이터·상태 계층**: DB, 캐시, 메시지, 오브젝트 스토리지, 모델/아티팩트 등 공고에 언급된 저장·전달 요소. 명시되지 않은 제품은 `데이터 저장소`, `배포 아티팩트`처럼 일반 레이블만 쓴다.
4. **네트워크·보안 계층**: ingress, TLS, VLAN, L4/L7, 접근 제어, 데이터 주권 경계 등 공고에 나온 연결·보안 제약.
5. **배포·운영 계층**: IaC, CI/CD, GitOps, 모니터링, 로그, 알림, 백업, 장애 대응, PoC·벤더 대응 중 공고에 나온 요소.
6. **흐름과 불확실성**: 동기 요청, 스트리밍, 비동기 이벤트, 데이터 동기화, 배포/관측 흐름을 구분한다. 공고가 연결 방식을 말하지 않았으면 점선과 `추론`/`확인 필요` 표기로 처리한다.

### 상세도 기준

이미지는 ImageGen으로 생성한 **가로 16:9 PNG**를 사용한다. 밝은 배경의 캐주얼한 아키텍처 다이어그램으로 만들되, 위 설계 항목을 단순 카드 나열로 축약하지 않는다. BubbleTab 수준의 상세도를 기준으로 다음을 지킨다.

- 좌측에는 사용자·운영자·외부 환경과 진입 경로를, 중앙에는 가장 큰 플랫폼/클러스터 경계를, 하단 또는 중앙 하단에는 데이터·상태 경계를, 우측에는 배포·관측·성능·복구 레인을 둔다. 공고 성격상 더 자연스러운 배치가 있으면 변형하되, 경계와 흐름은 유지한다.
- 중앙 플랫폼은 최소 2개 이상의 의미 있는 내부 계층(예: ingress → 서비스/워크로드 → GPU/데이터, 또는 Bare-metal → VM/Container → Kubernetes)으로 나누고, 상위 컨테이너와 하위 컴포넌트의 소속 관계를 보이게 한다.
- 기술이 충분히 구체적인 공고에서는 실제로 언급된 컴포넌트를 개별 노드로 분리하고 각 노드의 역할을 1줄로 쓴다. 공고가 희소하면 가짜 제품·서비스를 채우지 말고, 일반 노드와 `미확인`/`면접 확인` 경계를 사용한다.
- 적어도 하나의 끝에서 끝까지 이어지는 경로(요청·데이터·배포·운영 중 해당하는 경로)를 화살표로 완결해 보여 준다. 모든 화살표에는 필요한 경우 `HTTPS`, `CDC`, `배포`, `메트릭`, `비동기 이벤트`처럼 의미를 붙인다. 공고에 근거가 없으면 프로토콜이나 제품명을 발명하지 않는다.
- 동기 요청, 스트리밍, 비동기/데이터, 배포/텔레메트리처럼 성격이 다른 선은 색·실선/점선으로 구분하고, 하단 범례에서 뜻을 명시한다.
- 각 레인은 테두리와 제목을 갖고, 한글 레이블은 축소해도 읽을 수 있을 만큼 크게 쓴다. 텍스트가 작은 박스 안에 과밀하거나, 배경 장식이 흐름을 가리거나, 모호한 아이콘만 남는 이미지는 실패다.
- 공고에 명시된 오픈소스 또는 제품만 공식 스타일 로고를 넣는다. 특정 제품이 명시되지 않았으면 일반 레이블·범용 아이콘으로 처리한다. 우대사항 제품은 `우대 경험` 또는 `후보`의 점선 영역에 분리하고, 로고가 실제 채택처럼 보이게 하지 않는다.

### 1차 도출과 추론의 경계

- `1차 도출` 이미지에서는 JD에 명시된 기술, 환경, 책임, 제약을 굵은 실선/기본 색으로 표현한다. 배치 편의를 위한 연결은 가능하지만, 실제 통신·데이터 흐름으로 읽힐 수 있으면 `공고 기반 배치` 또는 `연결 방식 미확인`이라고 범례/캡션에서 밝힌다.
- `추론` 이미지에서는 가능한 목표 운영 모델을 더 구체화할 수 있다. 단, 추론 경로·영역에는 보라색 점선 또는 `INFERRED`/`추론` 배지를 사용하고, 실제 데이터 이동·워크로드 분리·보안 통제·벤더 채택이 미확정임을 화면 안과 캡션에서 명시한다.
- 각 이미지 아래에는 무엇이 공고 명시 사실이고, 어떤 연결/구성이 추론인지 1~2문장으로 설명한다.

### 생성 전·후 품질 게이트

생성 전 프롬프트에 다음을 명시한다: 제목, 16:9, 레인별 구성요소, 각 흐름의 시작·끝·선 스타일, 범례, 명시 기술과 추론 기술의 분리, 읽을 수 있는 큰 한글 레이블. 생성 후에는 다음을 확인한다.

1. 요청/운영/배포 중 적어도 하나의 실제 경로를 처음부터 끝까지 눈으로 따라갈 수 있는가?
2. 플랫폼 내부가 단일 큰 상자가 아니라 계층과 컴포넌트 관계로 구체화됐는가?
3. 데이터·상태, 보안·네트워크, 배포·관측 중 공고가 다루는 축이 독립 레인 또는 명확한 영역으로 드러나는가?
4. 로고·프로토콜·제품명이 공고의 명시 사실을 넘어서지 않는가?
5. 이미지의 큰 한글 레이블, 화살표, 범례가 렌더링 후에도 읽히며 여백·잘림·중복이 없는가?

위 기준을 충족하지 못하면 프롬프트를 보강해 재생성한다. 임베드 경로와 실제 파일 존재를 확인한다.

## 검증 및 완료

1. frontmatter와 내부 링크가 기존 vault 관례에 맞는지 확인한다.
2. 사용자 제공 전문이 있으면 callout에 원문 전체가 들어갔는지, URL 기반이면 스냅샷과 원본 링크가 있는지, 그리고 `<details>`가 남지 않았는지 확인한다.
3. Obsidian 리딩 뷰에서 callout을 열어 원문 내용이 실제로 보이는지 확인한다.
4. 모든 PNG 임베드가 렌더링되고, 여백·잘림·작은 텍스트 없이 읽히는지 확인한다.
5. 완료 보고에는 수정한 노트와 자산, 원문 범위, 검증 결과만 간결하게 적는다.
